# 视频流式推理 P1 实测：M1–M5、M9（RTX PRO 6000 / Colab G4）

**结论：配置 A（Qwen3.5-4B，64 token/帧，8 个问题每帧完整读出，15k KV 窗口）单路 BF16 端到端 P99 为 20.8 ms，通过 ≤40 ms 闸门，不需要退到 2B 或量化。** 推算表的理想合计是 17–21 ms，实测 P50 19.8 ms，整体现实系数约 1.0–1.2×，远低于报告担心的 2× 或 3–5×。但系数在各阶段分布很不均匀：前端（NVDEC + 预处理）比推算快 5–7 倍，LM 前向比推算慢约 1.3 倍，两者相互抵消。真正推翻推算的是**多路并发**：报告估计单卡 10–15 路 × 30 fps × N=8，实测 4B BF16 只能撑 2 路，FP8 也只有 2 路；0.8B 为 8 路，2B 为 4 路。

测量环境：NVIDIA RTX PRO 6000 Blackwell Server Edition（SM120，驱动 580.82.07），torch 2.14.1+cu130，transformers 5.23.0，flash-linear-attention 0.6.0，torchcodec 0.17.0+cu130。权重为 Hugging Face 原版 `Qwen/Qwen3.5-{0.8B,2B,4B}`，读出头随机初始化，只用于计时。2026-11-21 在一台 G4 上跑完，测完即关机。

## 测的是什么

原型代码在 [`speed/video_p1/stream.py`](../../speed/video_p1/stream.py)。每帧做一次前向，同时写入这一帧并读出 N 个问题块：

- 所有逐 token 的算子（norm、投影、MLP）对「B×T 个帧 token + B×N×20 个问题 token」只跑一次，4B 权重每帧只读一遍。
- GDN 层：帧 token 从持久递归状态 S 和 conv tail 继续增量计算，不重算前缀；问题块从帧更新后的状态快照分叉（每块一份初始状态），算完丢弃，不写回。
- 全注意力层：帧 query 看 KV 环形窗口（W 个槽，全部有效）和本帧因果部分；问题 query 看窗口、整帧和自己的块（块内双向，与 Glance 默认 `attn_mask` 一致）；只把帧的 K/V 写回窗口，RoPE 按绝对位置连续递增。
- 读出：Glance 结构的 presence/box 头（`dv.model.heads.BoxHeads`，经 `speed.box_readout.box_forward`）和 yes/no typed 头，读每块最后一个 token；另加一个 30 Hz 点积门控。
- 复用 glance-engine 的融合权重布局、融合逐元素算子、conv taps、`FP8Linear`（W8A8 E4M3，按通道/按 token 缩放）和 `FastVision` 视觉塔。

**正确性**：增量两帧 + 问题块的输出与 HF 整段前向对比，帧行与问题行的相对误差为 1.6%（0.8B）和 1.1–1.4%（4B），与 HF 自身换 batch 形状的 BF16 噪声（1.6% / 1.2%）相同，最小逐行余弦相似度 ≥0.9996（`raw/m1234_*.json` 的 `check`）。

**一处必须改的工程点**：PyTorch SDPA 一旦传入布尔 mask，在 SM120 上会退到 sm80 的 memory-efficient kernel，15k 窗口时每层 1.05 ms，比无 mask 的 flash 慢 7 倍。原型把注意力拆成两部分：窗口部分没有 mask，走 flash 并取出 log-sum-exp；本帧和问题块的局部部分（224 个 key）用显式 softmax 计算，再按 LSE 合并，结果精确（与 mask 版相对差 1.0–1.4%，处于噪声内）。4B 整步由此从 24.0 ms 降到 17.1 ms（15k 窗口），115k 窗口时从 84.8 ms 降到 26.6 ms。下文的数字都基于拆分版。

## 闸门结论

| 方案 | 单路端到端 P99 | ≤40 ms | 30 fps 下单卡最多几路（N=8，64 token/帧） |
|---|---:|---|---:|
| 4B BF16 | 20.8 | 通过 | 2（2 路时 P99 30.3；3 路服务时间 40.2 ms，跟不上） |
| 4B FP8 | 18.8 | 通过 | 2（2 路时 P99 25.6；3 路服务时间 33.6 ms，刚好跟不上） |
| 2B BF16 | 12.7 | 通过 | 4（4 路时 P99 26.4；8 路服务时间 45.5 ms） |
| 0.8B BF16 | 9.4 | 通过 | 8（8 路时 P99 35.5，余量很小；6 路 P99 26.2；10 路服务时间 40.2 ms） |

「跟得上」的判据是：按 30 fps 节拍连续送 900 帧，延迟不随时间增长。跟不上的行，节拍下的端到端延迟会无限积压，到第 900 帧已有几秒到几十秒，所以表里只给服务时间，即一个 tick 内 B 路各处理一帧所需的时间。

配置 A 在 4B 上单路通过，不需要退到 2B 或量化。如果目标是单卡多路，4B 即便用 FP8 也只有 2 路，2B 有 4 路，0.8B 有 8 路。

## 发现

1. **前端不是瓶颈。** NVDEC 解码 1080p H.264（8 Mbps，无 B 帧）的吞吐是 1,700 fps，单帧顺序取帧 P50 0.46–0.56 ms；在 GPU 上做 resize、normalize、拼滑动帧对和 patchify，共 0.1 ms。CPU 解码 P50 2.0 ms，P99 34 ms，不能用于流式。报告里 3–5 ms 的推算沿用了 ViCoStream 的数字，在这张卡和这条路径上偏高 5 倍以上。多路时解码按路数线性增长（16 路 8.1 ms），原因是原型逐路串行调用解码器，换成批量或多线程解码即可，暂时不用专门优化。注意：torchcodec 顺序取帧时，解码器内部可以提前解后面的帧；真实直播流要等包到达，单帧解码延迟应按约 1/1,700 s ≈ 0.6 ms 估计。

2. **滑动双帧对 ViT 是免费的。** Qwen 的图像模式本来就把单帧复制一份送进 Conv3d（temporal_patch_size=2），所以 (t−1, t) 滑动帧对与单帧的输入形状、计算量完全相同，实测也相同（4B 256²：2.08 对 2.08 ms）。报告说「滑动方式让 ViT 计算翻倍」，那是相对不重叠 tubelet（每两帧一次）而言的；相对单帧图像输入，滑动方式没有额外成本，也不用等下一帧。ViT 在 64 token 时被启动开销主导（4B 224² 与 256² 都是约 2.05 ms），FP8 几乎不省时间（2.05 对 2.08 ms），与报告引的「只省约 17%」方向一致，且收益更小。HF 原生 eager 视觉塔要 7.0 ms，必须用 FastVision + CUDA graph。另外，processor 的图像 `min_pixels`=65,536（即 256²），默认处理流程会把 224² 输入放大到 256²；视频 processor 的下限是 4,096 像素，没有这个问题。

3. **LM 是端到端的 86%，每步约 16 ms 的 GPU 时间分布在四处**（4B，T=64，N=8，eager kernel 时间，`raw/profile_4B.json`）：GEMM 8.5 ms；逐元素和其他算子 4.5 ms，每步 2,560 个 kernel；窗口注意力 1.6 ms；GDN 1.6 ms。合计 16.3 ms，与 CUDA graph 整步 17.0 ms 基本一致，所以 graph 之后启动开销已经不重要，时间都花在 kernel 本身。GEMM 的下限是 max(权重读取 7.14 GB ÷ 1.46 TB/s = 4.9 ms，224 token × 7.1 GFLOP ÷ 400 TFLOP/s = 4.0 ms) ≈ 4.9 ms，实测效率约 57%。剩下的差距主要来自**逐元素胶水算子**，它占 LM 的 28%，报告的推算里完全没有这一项。

4. **问题 token 决定了多路能撑几路，这是推算最大的漏洞。** 配置 A 每帧 224 个 token 里，160 个是问题 token（占 71%）。BF16 的计算/带宽拐点约为 275 FLOP/byte，也就是约 275 行，所以单路就已经接近计算受限。多路 batch 时省下的只是权重读取，计算量照样按路数线性增长。实测 4B 每多一路，LM 增加约 9.5 ms（B=4 时 42.2 ms，B=16 时 157 ms）。B=4 的 profile 显示：GEMM 19.4 ms（896 行，约 83% 峰值，已经计算受限），逐元素 11.0 ms，注意力 6.2 ms，GDN 5.2 ms。报告「8 路 × 64 token 共享一次权重读取」的推算只数了帧 token。即使 kernel 完美，4B 每路每帧也需要约 2 TFLOP（线性层 1.6 + 注意力 0.45），BF16 在 33 ms 内的理论上限只有约 6 路。

5. **注意力随窗口的增长比推算快，因为问题 query 也要读整个窗口。** 4B 单帧注意力（8 层，拆分版）：8k 为 2.2 ms，15k 为 2.9 ms，30k 为 4.4 ms，115k 为 12.6 ms；推算分别是 15k 约 2 ms、115k 约 5 ms。115k 时 224 个 query × 16 头 × 115k key 的计算量是 3.4 TFLOP，在 400 TFLOP/s 下最少也要 8.4 ms，所以这是计算下限，不是 kernel 效率问题。分层窗口（约 15k）的设计因此是必需的，不只是锦上添花。整步看，4B 在 115k 窗口下是 26.6 ms，仍在 40 ms 内。

6. **FP8 W8A8 的收益很小。** 4B LM 从 17.0 ms 降到 15.0 ms（−12%）；0.8B 反而略慢（7.1 → 7.4 ms），因为 0.8B 完全被逐元素算子和启动开销主导，按 token 动态量化又多出 kernel。

7. **CUDA graph 是硬性要求。** 不用 graph 时，4B 的 LM 为 44.7 ms，0.8B 为 33.5 ms（是 graph 的 4.7 倍），配置 A 会直接超出闸门。

8. **问题数的边际成本**：4B 在 T=64 时，N=0/8/32 分别为 10.3/17.0/37.8 ms（graph）；N=32 时每帧 704 个 token，GEMM 18 ms、逐元素 9.9 ms、GDN 4.9 ms（32 份状态快照的复制和分叉）。报告估计「N=32 完整读出约 25 ms」，实测约为 1.5 倍，这也说明 N>8 时必须做两级读出加轮转。

## 下一步建议

1. **P1 闸门已过，进入 P2（M6–M8，零训练精度、记忆跨度、长时稳定性）**，不用切换到 2B 或量化。延迟原型已经可以直接作为 M7、M8 的推理框架（状态和窗口都是增量的，可以连续跑 1 小时）。
2. **如果多路是部署目标，优先压缩每帧的问题 token，而不是继续抠 kernel。** 完整读出从 30 Hz 降到 5 Hz 轮转，靠 30 Hz 门控来保证「何时」的分辨率，平均每帧 token 从 224 降到约 91。按每路边际成本估计，4B 可以从 2 路提到约 4–5 路。这需要在 M9 中加一组「轮转 + 门控」的实测，确认门控精度可以接受（对应图像侧的轻量门控对照实验）。
3. **工程上收益最大的两项**：(a) 把约 2,500 个逐元素 kernel 融合掉（rope、gate、cat/scatter、norm），预计可以从 LM 中拿回 2–3 ms；(b) 移植 glance-engine 已有的 `gdn_branch` 融合分叉 kernel 和 `branch_attention`，避免按块复制状态快照、按问题块单独做 attention。按 profile 估计，4B 配置 A 可以从 17 ms 降到约 11–12 ms，多路下收益更大。
4. **量化**：FP8 W8A8 对单路只有 12% 收益，不值得因此牺牲数值精度；如果要提高多路密度（计算受限），NVFP4 的 2 倍算力更有意义，可以放到 P5。
